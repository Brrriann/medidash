# 운영 준비 체크리스트 — 300명 동시접속 대응 (후속 단계)

> **현재 빌드는 「동작 테스트 버전」입니다.** 기능 흐름(인체 지도 → 원료 → 소싱 → 마진)을
> 끝까지 검증하는 것이 목적이며, 대규모 동시접속 최적화는 이 문서의 항목으로 **미뤄둡니다**.
> 실서비스(수강생 ~300명 동시접속) 오픈 전에 아래를 순서대로 적용합니다.

## 왜 지금은 미뤄도 되나

- 아키텍처(Cloudflare Workers/Vercel + Supabase)는 **서버리스 + 매니지드 DB**라 컴퓨트는 자동 확장됩니다.
  300 동접은 초당 수십 요청 수준이라 구조 변경 없이 감당됩니다.
- 병목은 "규모"가 아니라 아래의 **디테일**(자산 크기·캐싱·과금·동시성)입니다. 테스트 버전에서
  기능을 확정한 뒤 한 번에 적용하는 편이 효율적입니다.

## 적용 항목 (우선순위 순)

### P0 — 오픈 전 필수

| # | 항목 | 문제 | 조치 | 예상 작업 |
|---|---|---|---|---|
| 1 | **3D 모델 경량화** | `public/models/body.glb` 7.9MB — 첫 방문마다 다운로드, 모바일·대역폭 부담 | Draco/meshopt 압축(→1.5~3MB), `Cache-Control: immutable` 장기 캐시, Cloudflare 정적 자산(이그레스 무료) 활용 | 0.5d |
| 2 | **읽기 데이터 캐싱** | 분류·도매 캐시를 페이지 SSR마다 Supabase 조회 | 분류는 불변→빌드 타임/`revalidate` 장기 캐시, 도매 캐시는 월 1회 갱신이므로 1시간 ISR → DB 조회 ~99% 감소 | 0.5d |
| 3 | **Supabase Pro ($25/월)** | 무료 티어는 1주 미사용 시 프로젝트 자동 일시정지·백업 없음·낮은 상한 | 실서비스 프로젝트는 Pro 이상. 커넥션 풀(Supavisor) 확인 | 결제/설정 |
| 4 | **가입 코드 동시성** | 개강일 동시 가입 시 `조회→used+1`이 초과 사용 허용 가능 | `update ... set used = used + 1 where code = ? and used < max_uses` 조건부 원자 업데이트 + affected-row 확인. `invite_codes`에 잔여 검증을 DB 함수(RPC)로 이관 | 0.5d |
| 5 | **AI 호출 비용·율제한** | 300명이 썸네일·상품명 무제한 생성 시 API 비용 급증 (진짜 리스크는 인프라가 아니라 여기) | 1인당 일일 생성 횟수 제한 + 동일 입력 결과 캐시. **크레딧 차감은 범위 밖(2차 계약)** 이므로 최소 방어선만. 정책값(1일 N회)은 발주처 결정 필요 | 1d + 정책 |

## 진행 방식

1. **테스트 버전(현재)**: 기능 확정 + 발주처 QA. env 없이 mock 모드로도 UI 확인 가능.
2. **파일럿**: Supabase Pro 연결 + P0(1~5) 적용 → 소수(10~20명) 베타.
3. **정식 오픈**: P1(6~10) 완료 + 부하 테스트 통과 → 300 동접 대응.

> 정책 결정이 필요한 항목: **AI 1인당 일일 생성 횟수 한도(#5)**, **Supabase 플랜 결제(#3)**.
